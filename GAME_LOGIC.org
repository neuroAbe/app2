* Overview

** Vision
CatchFeelings combines Pokemon's exploration and encounters with The Sims' relationship building to create a unique dating game experience.

** Core Pillars
1. *Exploration* - Discover locations and people organically
2. *Encounters* - Meet real users through proximity-based matching
3. *Relationships* - Build meaningful connections through activities
4. *Progression* - Level up and unlock new content

** Technical Stack
- Mobile: React Native (Expo)
- Backend: Supabase (PostgreSQL, Realtime, Auth)
- Authentication: Clerk
- Game Engine: Custom 2D engine (mobile), Phaser (web)

* Core Game Loop

** Daily Session Flow
#+BEGIN_SRC
Session Start
    ↓
Check Notifications → View Messages
    ↓
Choose Activity:
    → Explore World (walk around)
    → Check Quests (daily/weekly)
    → Manage Relationships (view connections)
    → Visit Home (customize, rest)
    ↓
Exploration Loop:
    Walk → Encounter → Interact → Match/Skip → Continue
    ↓
Plan/Execute Date Activity
    ↓
Check Progress (XP, quests, achievements)
    ↓
Session End (save state)
#+END_SRC

** Moment-to-Moment Gameplay
1. Player opens app
2. Views map with current location
3. Decides where to go (coffee shop, park, etc.)
4. Walks towards destination using joystick
5. Random encounter triggers (proximity-based)
6. Mini-profile appears with ice breaker
7. Conversation or mini-game
8. Match or continue exploring
9. Check quest progress
10. Receive notifications for matches
11. Plan activities with connections

** Win Conditions
- Primary: Build meaningful connections (subjective)
- Secondary: Complete quests, level up, unlock content
- Tertiary: Collect badges, achievements

* System 1: Player Movement and World Exploration

** 1.1 Movement Mechanics

*** Use Case 1.1.1: Basic Movement
**** Preconditions
- Player is logged in
- World is loaded
- Player has valid spawn position

**** Trigger
- Player touches virtual joystick (mobile)
- Player presses arrow keys/WASD (web)

**** Flow
1. Input system captures direction vector (x, y)
2. Normalize vector for diagonal movement
3. Multiply by speed constant (3 units/frame)
4. Calculate new position: newPos = currentPos + (vector * speed * deltaTime)
5. Check collision with world tiles
6. If no collision: Update player position
7. If collision: Stop movement in that direction
8. Update player sprite direction (up/down/left/right)
9. Update camera to follow player (center on screen)
10. Save position to database (debounced every 2 seconds)

**** Postconditions
- Player position updated in local state
- Camera adjusted to keep player centered
- Position saved to database (eventually)

**** Edge Cases
- Player moves off-screen: Camera follows, world scrolls
- Player moves to world boundary: Collision prevents exit
- Rapid direction changes: Last valid direction used
- Network failure during save: Position cached locally, synced when reconnected

*** Use Case 1.1.2: Camera System
**** Flow
1. Calculate camera offset: cameraPos = screenCenter - playerPos
2. Apply transform to world container
3. Render only visible tiles (viewport culling)
4. Update HUD elements (stay fixed to screen)

*** Use Case 1.1.3: Collision Detection
**** Flow
1. Get player's bounding box (x, y, width, height)
2. Get new position after movement
3. Query tiles in that area
4. Check tile types: walkable vs solid
5. If solid tile overlaps player bbox: Return collision=true
6. If all walkable: Return collision=false

**** Tile Types
- =grass= - Walkable, base terrain
- =path= - Walkable, roads
- =water= - Non-walkable, decorative
- =building= - Non-walkable, interactable
- =tree= - Non-walkable, obstacle
- =flower= - Walkable, decorative

* System 2: Encounter System

** 2.1 Proximity-Based Encounters

*** Use Case 2.1.1: Random Encounter Trigger
**** Preconditions
- Player is in encounter zone
- Player has moved > 50 units since last encounter
- Cooldown period elapsed (30 seconds)
- Available users in proximity database

**** Trigger
- Random probability check every second
- Probability = zoneEncounterRate * timeOfDayMultiplier * userDensity

**** Flow
1. Game loop checks encounter probability
2. Roll random number (0-1)
3. If roll < probability: Trigger encounter
4. Query database for nearby users:
   #+BEGIN_SRC sql
   SELECT * FROM user_profiles
   WHERE ST_Distance(position, player_position) < 1000
   AND is_online = true
   AND clerk_user_id != current_user
   AND clerk_user_id NOT IN (blocked_users)
   ORDER BY RANDOM()
   LIMIT 1
   #+END_SRC
5. Load encounter data
6. Pause player movement
7. Show encounter animation (screen shake, music)
8. Display encounter screen

**** Postconditions
- Game paused
- Encounter UI visible
- User profile loaded
- Encounter logged in database

**** Edge Cases
- No users available: Show NPC encounter or skip
- User goes offline mid-encounter: Show "User left" message
- Network failure: Cache encounter, retry when reconnected
- User blocks/reports during encounter: End encounter immediately

*** Use Case 2.1.2: Encounter Screen Display
**** UI Elements
1. *User Avatar* - Large display, animated
2. *Basic Info* - Name, age, distance
3. *Ice Breaker* - Random question or prompt
4. *Action Buttons*
   - "Say Hi" (start conversation)
   - "Play Game" (mini-game challenge)
   - "Keep Walking" (skip encounter)

**** Flow
1. Fade in encounter screen
2. Animate user avatar entrance
3. Display info with slide-in animation
4. Show random ice breaker from pool:
   - "What's your favorite coffee order?"
   - "Last concert you went to?"
   - "Guilty pleasure TV show?"
5. Wait for user action (30 second timeout)

*** Use Case 2.1.3: Ice Breaker System
**** Ice Breaker Categories
- Food & Drink
- Entertainment
- Hobbies
- Travel
- Lifestyle
- Hypotheticals

**** Selection Algorithm
1. Check both users' interests
2. Find common categories
3. Prioritize questions about shared interests
4. Fallback to general questions
5. Never repeat same question to same user pair

** 3.3 Compatibility Scoring

*** Use Case 3.3.1: Calculate Match Score
**** Factors
1. *Shared Interests* (30%)
   - Common hobbies
   - Similar preferences
   - Overlapping friend groups

2. *Conversation Quality* (25%)
   - Response rate
   - Message length
   - Time between responses
   - Emoji/tone analysis

3. *Activity Compatibility* (20%)
   - Similar activity preferences
   - Matching energy levels
   - Compatible schedules

4. *Location* (15%)
   - Proximity
   - Shared locations visited
   - Similar hangout spots

5. *Social Graph* (10%)
   - Mutual connections
   - Similar social patterns

**** Algorithm
#+BEGIN_SRC python
def calculate_compatibility(user1, user2):
    score = 0

    # Shared interests
    common_interests = set(user1.interests) & set(user2.interests)
    score += (len(common_interests) / max(len(user1.interests), len(user2.interests))) * 30

    # Conversation quality (from ML model)
    conv_quality = analyze_conversation_sentiment(conversation)
    score += conv_quality * 25

    # Activity compatibility
    activity_overlap = calculate_activity_overlap(user1, user2)
    score += activity_overlap * 20

    # Location proximity
    distance = calculate_distance(user1.location, user2.location)
    location_score = max(0, 15 - (distance / 100))
    score += location_score

    # Social graph
    mutual_friends = count_mutual_connections(user1, user2)
    score += min(mutual_friends * 2, 10)

    return min(100, score)
#+END_SRC

** 4.2 Relationship Meters

*** Use Case 4.2.1: Track Relationship Metrics
**** Metrics
1. *Friendship* (0-100)
   - Increases: Regular conversations, shared activities
   - Decreases: Long periods without contact, negative interactions

2. *Romance* (0-100)
   - Increases: Date activities, compliments, gifts
   - Decreases: Missed dates, one-sided effort

3. *Compatibility* (0-100)
   - Calculated from shared activities
   - How well you mesh in activities
   - Updated after each interaction

4. *Trust* (0-100)
   - Increases: Consistent behavior, honesty, vulnerability
   - Decreases: Flakiness, dishonesty detected

**** Update Formula
#+BEGIN_SRC python
def update_relationship_meter(relationship, action):
    # Base change from action
    base_change = ACTION_VALUES[action.type]

    # Time decay (relationships decay without interaction)
    days_since_interaction = (now - relationship.last_interaction).days
    decay = -0.5 * days_since_interaction

    # Apply change with diminishing returns
    if relationship.friendship > 80:
        base_change *= 0.5  # Harder to improve at high levels

    # Update meter
    relationship.friendship += base_change + decay
    relationship.friendship = clamp(relationship.friendship, 0, 100)

    # Check for stage transition
    check_stage_transition(relationship)
#+END_SRC

** 6.2 Quest Management

*** Use Case 6.2.1: Quest Assignment
**** Flow
1. Daily reset trigger (midnight)
2. Generate daily quests for user:
   #+BEGIN_SRC python
   def generate_daily_quests(user):
       quest_pool = DAILY_QUEST_TEMPLATES

       # Personalize based on user behavior
       if user.favorite_activity == 'coffee':
           prioritize_coffee_quests()

       # Ensure variety (don't repeat yesterday's quests)
       available = filter_out_recent(quest_pool, user.recent_quests)

       # Select 3-5 quests
       selected = random.sample(available, k=3)

       # Create quest instances
       for quest_template in selected:
           create_quest_instance(user, quest_template)
   #+END_SRC
3. Save to database
4. Send notification: "New daily quests available!"

*** Use Case 6.2.2: Track Quest Progress
**** Flow
1. User performs action (sends message, visits location, etc.)
2. Action event fired
3. Quest system receives event
4. Query active quests:
   #+BEGIN_SRC sql

* Edge Cases and Error Handling

** Network and Connectivity

*** Edge Case 1: Network Failure During Encounter
**** Scenario
- User encounters another user
- Network connection lost mid-conversation

**** Handling
1. Detect connection loss
2. Show "Connection lost" banner
3. Buffer messages locally
4. Attempt reconnection with exponential backoff
5. If reconnected within 2 minutes:
   - Sync buffered messages
   - Resume encounter
6. If not reconnected:
   - Save encounter state to local storage
   - Show "Saved draft" notification
   - When back online: Option to "Continue conversation"

*** Edge Case 2: Database Write Failure
**** Scenario
- User completes activity
- Database write fails (timeout, constraint violation)

**** Handling
1. Catch database error
2. Log error with context
3. Queue operation for retry:
   #+BEGIN_SRC python
   retry_queue.add({
     'operation': 'save_activity_completion',
     'data': activity_data,
     'attempts': 0,
     'max_attempts': 5
   })
   #+END_SRC
4. Show user: "Saving... please wait"
5. Retry with exponential backoff
6. If all retries fail:
   - Save to local persistent storage
   - Show: "Changes will sync when connection improves"
   - Background job retries when app reopens

** Race Conditions

*** Edge Case 3: Simultaneous Match Requests
**** Scenario
- User A and User B both request match at same time
- Could create duplicate match records

**** Handling
1. Use database constraint: =UNIQUE(user1_id, user2_id)= with ordered IDs
2. Handle unique violation in code:
   #+BEGIN_SRC python
   try:
       create_match(user1, user2)
   except UniqueViolationError:
       # Match already exists, just update status
       update_match_status(user1, user2, 'confirmed')
   #+END_SRC
3. Use database transactions
4. Optimistic locking with version numbers

*** Edge Case 4: Activity Booking Conflict
**** Scenario
- User tries to book activity at same time as another activity

**** Handling
1. Before creating activity invitation:
   #+BEGIN_SRC sql
   SELECT COUNT(*) FROM activities
   WHERE creator_id = current_user
   AND status = 'scheduled'
   AND scheduled_time BETWEEN :start_time - INTERVAL '2 hours'
                          AND :start_time + INTERVAL '2 hours'
   #+END_SRC
2. If conflict found:
   - Show warning: "You have another activity at [time]"
   - Option to cancel existing or choose different time
3. Enforce max concurrent activities (3)

** User Behavior Edge Cases

*** Edge Case 5: User Goes Offline During Activity
**** Scenario
- Activity in progress
- One participant's app crashes or they go offline

**** Handling
1. Detect participant disconnection (heartbeat timeout)
2. Pause activity timer
3. Show to remaining participants: "[Name] disconnected"
4. Wait 3 minutes
5. Options:
   - "Wait for [Name]" (extends wait)
   - "End Activity" (partial credit)
6. If participant returns within window:
   - Resume activity
   - Compensate for lost time
7. If timeout:
   - End activity
   - Partial rewards to present participants
   - Log no-show for disconnected user

*** Edge Case 6: Spam Messages
**** Scenario
- User sends 20 messages in 10 seconds
- Could be harassment or bot behavior

**** Handling
1. Rate limiting:
   #+BEGIN_SRC python
   RATE_LIMIT = 5  # messages
   RATE_WINDOW = 10  # seconds

   if count_recent_messages(user, RATE_WINDOW) > RATE_LIMIT:
       raise RateLimitError("Slow down! Wait a few seconds.")
   #+END_SRC
2. Show warning to user
3. Implement exponential backoff
4. If persists:
   - Temporary chat timeout (5 minutes)
   - Flag for review
5. Log incident

*** Edge Case 7: User Deletes Account Mid-Conversation
**** Scenario
- User A deleting account
- User B has active conversation with User A

**** Handling
1. Soft delete user profile:
   #+BEGIN_SRC sql
   UPDATE user_profiles
   SET deleted_at = NOW(),
       is_online = false
   WHERE clerk_user_id = :user_id
   #+END_SRC
2. Anonymize data:
   - Replace display_name with "Deleted User"
   - Remove photos
   - Clear personal info
3. Keep conversation history (with anonymized sender)
4. Remove from:
   - Encounter pool
   - Active activities
   - Friends lists
5. Notify matches: "This user has left CatchFeelings"
6. Allow 30-day grace period for account recovery

** Game Logic Edge Cases

*** Edge Case 8: Negative Relationship Meter
**** Scenario
- Multiple no-shows and long inactivity
- Relationship meter drops below 0

**** Handling
1. Clamp at 0: =relationship.friendship = max(0, new_value)=
2. At 0 friendship for 30 days:
   - Suggest: "It seems you've lost touch. Archive this connection?"
   - Don't force, let user decide
3. If both users inactive for 90 days:
   - Auto-archive relationship
   - Can be restored if either user reaches out

*** Edge Case 9: Level Up During Activity
**** Scenario
- User gains enough XP mid-activity to level up
- Level up animation would interrupt gameplay

**** Handling
1. Queue level up event:
   #+BEGIN_SRC python
   if user.xp >= xp_for_next_level(user.level):
       level_up_queue.add(user.id)
       # Don't process now
   #+END_SRC
2. Continue activity uninterrupted
3. After activity completes:
   - Show level up animation
   - Display all rewards
4. If multiple level ups: Show combined celebration

*** Edge Case 10: Collision with Another Player
**** Scenario
- Two real players walk into same space in game world

**** Handling
1. Detect bounding box overlap
2. Don't prevent movement (not solid collision)
3. Instead, trigger encounter:
   - "You bumped into [Name]!"
   - Instant encounter opportunity
   - Higher chance of match (serendipity bonus)
4. If declined, allow overlap for 5 seconds
5. Slight repulsion force to naturally separate avatars

**** Handling

   - Medium confidence (0.6-0.9): Warn but allow
   - Low confidence (<0.6): Allow, log for review
2. User can appeal:
   - "This was flagged by mistake"
   - Human review
3. Feedback loop improves AI over time

** Optimization Strategies

*** Database Query Optimization
1. *Indexes* - Add indexes for common queries:
   - User location (spatial index)
   - Active users (WHERE is_online = true)
   - Unread messages
   - Scheduled activities

2. *Query Patterns*
   #+BEGIN_SRC sql
   -- BAD: N+1 query
   for user in users:
       get_user_profile(user.id)

   -- GOOD: Batch query
   SELECT * FROM user_profiles WHERE id IN (:user_ids)
   #+END_SRC

3. *Connection Pooling* - Reuse database connections
4. *Prepared Statements* - Reduce query parsing time

*** Proximity Search Optimization
1. *Spatial Indexing* - PostGIS for geographic queries
   #+BEGIN_SRC sql
   -- Use spatial index for nearby users
   SELECT * FROM user_profiles
   WHERE ST_DWithin(
     ST_Point(position_x, position_y)::geography,
     ST_Point(:player_x, :player_y)::geography,
     1000  -- meters
   )
   AND is_online = true
   LIMIT 10;
   #+END_SRC

2. *Grid-Based Bucketing* - Divide world into zones
   - Only query users in same zone or adjacent zones
   - Reduces search space

3. *Caching* - Cache nearby users for 30 seconds
   - Reduces database hits
   - Background refresh

*** Rendering Optimization

1. *Viewport Culling* - Only render visible tiles
   #+BEGIN_SRC javascript
   const visibleTiles = tiles.filter(tile =>
     tile.x + tileSize > cameraX &&
     tile.x < cameraX + screenWidth &&
     tile.y + tileSize > cameraY &&
     tile.y < cameraY + screenHeight
   );
   #+END_SRC

2. *Sprite Batching* - Combine draw calls
3. *Asset Optimization*
   - Use sprite sheets
   - Compress images (WebP)
   - Lazy load assets

4. *Frame Rate Management*
   - Cap at 60 FPS
   - Skip rendering if behind schedule
   - Reduce quality on low-end devices

*** Realtime Updates Optimization

1. *Rate Limiting* - Position updates every 2 seconds, not every frame
2. *Delta Compression* - Send only changed data
3. *Channel Management* - Subscribe only to relevant channels:
   - Own conversations
   - Nearby users (only in encounter zones)
   - Active activities

*** Memory Management

1. *Conversation History* - Load last 50 messages, lazy load older
2. *World Tiles* - Unload far-away chunks
3. *Image Caching* - Limit cache size, use LRU eviction
4. *Event Listeners* - Clean up on unmount

from redis import Redis

redis = Redis()

def check_rate_limit(user_id, action, limit, window):
    key = f"rate_limit:{user_id}:{action}"
    current = redis.incr(key)

    if current == 1:
        redis.expire(key, window)

    if current > limit:
        raise RateLimitError(f"Too many {action} requests")

    return current
#+END_SRC
